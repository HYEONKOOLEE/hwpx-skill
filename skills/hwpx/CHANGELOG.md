# 변경 이력

## v1.4 — 2026-09-05 (새 문서 생성 워크플로 C · R5~R9 신설)

양식 없이 **처음부터 만드는** 사내 규정·매뉴얼·지침서를 5종 연달아 작성하면서, 기존
A(템플릿 치환)·B(기존 문서 편집) 두 갈래로는 담기지 않는 함정이 반복해서 나왔다.
그중 하나는 사용자가 화면을 보고 나서야 발견됐다 — **본문 전체가 가운데 정렬로 나온 것.**

### 원인

`python-hwpx`의 `set_paragraph_format()`은 인자를 생략하면 그 속성을 "건드리지 않는" 것이
아니라, **그 속성을 이미 가진 기존 `paraPr`를 재사용**한다. 그래서:

| 생략한 인자 | 실제로 벌어진 일 |
|---|---|
| `alignment` | 앞서 CENTER로 만든 `paraPr`가 재사용되어 **조·항·호 본문이 전부 가운데 정렬** |
| `page_break_before` | 페이지나눔이 켜진 `paraPr`가 재사용되어 **단락 141개에 쪽나눔** → 37쪽 문서가 153쪽 |

검증 3종(`verify_hwpx.py`, `contentLoss`, `exportHwpVerify`)은 셋 다 PASS를 줬다.
텍스트도 쪽 구조도 "손실"은 없었기 때문이다. **보기 흉한 문서는 무결성 검사에 걸리지 않는다.**

### 추가 — C. 새 문서 생성 워크플로

0단계 작업 유형 판별표에 **C** 갈래를 신설했다. "규정 만들어줘", "매뉴얼 써줘"처럼
쓸 만한 양식이 없는 요청은 이제 A로 우겨넣지 않고 C로 간다. C는 빌더 클래스(`hlib.py`
패턴) — 셀 전용 `paraPr` 2종(좌·중앙)을 미리 확보해 두고 모든 단락에 **모든 서식 속성을
항상 명시적으로** 넘긴다.

### 신설 규칙

| 규칙 | 내용 |
|---|---|
| **R5** | `set_paragraph_format()`에 **모든 속성을 항상 명시**한다. 생략은 "유지"가 아니라 "남의 것 재사용"이다 |
| **R6** | `HwpxDocument.new()`가 만드는 `<hp:p id>` 중복을 **검출로 끝내지 말고 저장 직후 재부여**한다 (v1.3 검사 6번이 잡아내지만 고쳐 주지는 않는다) |
| **R7** | 표 머리행은 **연한 색 + 가운데 정렬**, 본문 행은 **왼쪽 정렬**. 짙은 남색 채움과 전면 가운데 정렬은 쓰지 않는다 |
| **R8** | `orientation='portrait'`를 넘기지 않는다 — OWPML은 `WIDELY`/`NARROWLY`만 허용하며, A4 세로는 `WIDELY` + 59528×84188이다 |
| **R9** | 저장은 **파이프라인 5단계**로 고정: `save_to_path` → id 중복 재부여 → `fix_namespaces` → `clear_layout_cache` → `verify_hwpx` |

### 서식 기본값 (R7 상세)

- 표 머리행 채움 `#E9EEF6`(아주 연한 남색), 라벨 칸 `#F4F6F9`
- 머리행 텍스트 **가운데 정렬**, 2행 이하 본문 **왼쪽 정렬**
- 1행짜리 정보 표(제정일·시행일 등)와 결재란은 예외적으로 전부 가운데 정렬
- 본문 줄간격 160%, 표 셀 140%

### 검증 절차 보강

`verify_hwpx.py` PASS만으로는 R5 위반을 잡을 수 없다. C 워크플로는 저장 후 **정렬·페이지나눔
분포를 직접 세어** 확인한다.

```python
from collections import Counter
print(Counter(pp.get('align') for pp in root.iter(H+'paraPr')))
print(sum(1 for pp in root.iter(H+'paraPr') if pp.get('pageBreakBefore')=='1'))
```

### 손대지 않은 것

- `scripts/` 5종 — v1.3 그대로. R5·R7은 생성 시점의 규칙이라 사후 검사로 잡을 수 없다.
- `references/` 4종, `assets/` 2종 — 무변경.

## v1.3 — 2026-09-04 (표 구조 무결성 · R4 신설)

서식 문서의 표에서 빈 행을 지운 뒤 세로 병합 범위를 맞추지 않아 **한글이 파일 자체를
거부하는** 사고가 있었다. 더 심각한 문제는 **기존 검증 3종이 모두 PASS를 줬다**는 점이다.
규칙(R4)과 자동 검사 2종을 넣어, 같은 실수가 조용히 통과하지 못하게 했다.

### 원인

별첨 서식 하나를 채우는 작업이었다. 관공서 서식은 겉보기에 여러 표처럼 보여도 실제로는
**전체가 표 하나**이고, 왼쪽 라벨 칸이 크게 세로 병합되어 있는 경우가 많다. 문제의 서식은
18행 표에 `rowAddr=7 / rowSpan=11`짜리 라벨 셀이 있었다.

커리큘럼 7행만 쓰고 남는 빈 행 3개를 지웠는데 `rowSpan`은 11로 그대로 뒀다. 표는 15행인데
셀 하나가 18행까지 걸쳐 있다고 주장하는 상태가 됐고, 한글은 이 모순을 만나면 문서를
**열지 않는다** — "파일을 읽거나 저장하는데 오류가 있습니다."

여기에 `rowAddr`를 0부터 순차 재부여한 것이 겹쳐 병합 셀 주소까지 흔들렸다.

검증이 전혀 걸러 주지 못했다.

| 도구 | 결과 |
|---|---|
| `verify_hwpx.py` (v1.2) | PASS |
| `@rhwp/core` `contentLoss` | `count: 0` (무손실) |
| `@rhwp/core` `exportHwpVerify` | `pageCountBefore == pageCountAfter`, `recovered: true` |

셋 다 텍스트·쪽수 보존만 본다. **구조 무결성은 아무도 보지 않았다.**

### 추가

- **`SKILL.md` 절대 규칙 R4 신설** — "표의 행·열을 지우거나 추가했으면 병합(span)
  정합성을 맞춘다". 기존 R1~R3과 나란히 배치했다. 행 삭제 5원칙(꼬리 행만 삭제 /
  `rowAddr` 재부여 금지 / `rowSpan`·`rowCnt` 보정 / 저장 전 검사 / 애매하면 빈 행으로
  남긴다), 보정 함수 `fix_and_check_table()`, 편집 전 표 구조 조사 코드를 함께 실었다.
- **`scripts/verify_hwpx.py` 검사 5번** — 표 병합 정합성. 각 표의 `<hp:tr>` 수를 세고
  모든 셀에 대해 `rowAddr + rowSpan <= 행 수`, `colAddr + colSpan <= colCnt`를 확인한다.
  `rowCnt` 속성과 실제 행 수 불일치도 함께 잡는다. 중첩 표를 오검출하지 않도록 직계 자식
  `<hp:tr>`만 센다. 표준 라이브러리(`xml.etree`)만 쓰므로 추가 의존성이 없다.
- **`scripts/verify_hwpx.py` 검사 6번** — 단락 id 중복. `<hp:p>`를 복제해 여러 줄을 만들
  때 id를 재사용하면 한글이 파일을 거부한다.
- **`SKILL.md` 트러블슈팅 절** — "한글이 파일을 못 열 때" 의심 순서 6가지. 원인 규명 전에도
  `.hwpx`를 먼저 전달해 사용자를 기다리게 하지 않는다는 원칙을 명시했다.
- **셀 여러 줄 교체 패턴 `set_cell()`** — 기존 `<hp:p>`를 복제할 때 서식 ID를 같은 표의
  채워진 셀에서 가져오는 방법, 새 id 부여, XML 선언 보존 주의사항.

### 수정

- **0-A단계** — `contentLoss: 0` + `recovered: true`가 "한글에서 열린다"는 뜻이 아님을 경고로 명시.
- **산출 형식 규약** — 표 구조를 변경한 문서는 `.hwp`와 `.hwpx`를 **항상 함께 전달**한다.
- **필수 후처리 3** — 검사 항목을 6개 → 8개 표로 정리하고, "이 스크립트도 검사하지 않는 것"
  절을 추가(XML 선언 형태 / 역변환 어댑터 실패 / 실제 한글 앱에서의 열림).
- **치환 절차 A·B** — `[2-1] 표 구조 조사`, `[4-1] span 보정 + assert` 단계 삽입.
- **주의사항** — 19개 → 23개. 5·12·13·14번이 R4 관련 신설 항목.
- **Quick Reference** — "표의 빈 행 삭제", "한글이 파일을 읽거나 저장하는데 오류" 행 추가.

### 손대지 않은 것

- `references/` 4종, `assets/` 2종, `evals/` — 변경 없음.
- `scripts/`의 나머지 4종(`clear_layout_cache.py`·`fix_namespaces.py`·`autofit_table_rows.py`·
  `hwp_bridge.mjs`) — 변경 없음.
- ZIP-level 치환 로직과 A/B 작업 유형 판별 — 변경 없음.

## v1.2 — 2026-09-01 (스킬 범위 한정 · 단독 설치)

배포판을 받은 사용자가 "rhwp 관련 스킬도 추가로 설치해야 하나?"라고 오해하는 문제를 없앴다.
이 스킬의 범위를 **`.hwp`/`.hwpx` 읽기·편집·생성·저장**으로 한정하고, 누름틀 채우기·메일머지
축은 완전히 분리했다. **이제 이 폴더 하나로 완결된다.**

### 원인

`SKILL.md`가 두 곳에서 다른 스킬을 지목하고 있었다.

1. YAML frontmatter `description` 끝의 "…메일머지하는 작업은 rhwp-form-fill 스킬을 쓸 것"
   — 스킬 목록에 색인되는 문장이라 설치 직후 사용자 눈에 바로 띈다.
2. 0-A단계 판정표의 "누름틀 서식에 값만 채우는 작업 → rhwp-form-fill 스킬로 전환" 행.

여기에 의존 패키지 이름 `@rhwp/core`(npm 라이브러리)가 겹쳐 "rhwp = 별도 설치물"로 읽혔다.
저장소 `README.md`에는 rhwp 관련 설치 안내가 원래 없었으므로, 설치 자체에는 영향이 없었다.

### 수정

- **frontmatter `description`** — rhwp-form-fill 분기 문장 삭제.
  "다른 스킬을 함께 설치할 필요가 없다"를 앞머리에 명시하고, 성격을 "생성·읽기·편집·템플릿 치환"에서
  **"읽고·편집하고·생성해 저장하는 단독 스킬"**로 다시 규정.
- **0-A단계 판정표** — 누름틀 분기 행 삭제. 이제 `.hwpx` / `.hwp` / `.hml` 3행만 남는다.
- **주의사항 15번** — `@rhwp/core` 뒤에 "(npm 라이브러리, 별도 스킬 아님)" 병기.

### 추가

- **「이 스킬의 범위」 표**(개요 직하) — 한다 4항목 / 하지 않는다 4항목을 대조.
  범위 밖은 누름틀 자동 채우기·메일머지, 한글 앱 매크로 자동화, PDF 변환, Word 처리.
- **`@rhwp/core` 구분 박스** — `SKILL.md` 설치 섹션과 `README.md` 의존 패키지 섹션 양쪽에 삽입.
  npm 패키지와 동명의 별도 CLI·스킬을 표로 갈라 놓고, `npm i` 실패해도 `.hwpx` 작업은
  전부 정상 동작한다는 점을 명시.
- **주의사항 19번 신설** — 범위 밖 요청이 와도 **다른 스킬 설치를 안내하지 않는다.**
  범위 밖임을 한 줄로 알리고 ZIP-level 치환이라는 대안을 제시하도록 행동 규칙화.
- `README.md` 갱신 — 제목에 `.hwp` 포함, v1.1의 `.hwp` 직접 처리 기능을 사용 예시에 반영,
  「범위 밖」 절 신설. (README가 v1.0에 머물러 v1.1 기능을 반영하지 못했던 것도 함께 해소)

### 손대지 않은 것

- 0-A단계 변환 절차 자체, `scripts/hwp_bridge.mjs`, `@rhwp/core` 의존성
  — `.hwp` 직접 읽기·저장 기능의 핵심이므로 그대로 유지한다.
- 문서 생성·편집 절차, 서식 규격, `references/` 4종, `scripts/` 5종, `assets/` 2종, `evals/`.

### 확인 사항

- 개인정보(이름·이메일·연락처)·소속 기관명·고객사명 **없음**. 배포 전 전수 스캔 완료.
- `assets/`의 두 양식은 자리표시자로만 채워진 일반 공공기관 서식 샘플.
  `form2.hwp` 차례에 남은 `유네스코 한국위원회 사업지원` 예시 문구는 README에 명시.
- `SKILL.md` 선두 **UTF-8 BOM 없음**. BOM이 붙으면 YAML frontmatter가 통째로
  파싱되지 않아 스킬 설명과 트리거 문구가 색인되지 않는다.
  Windows PowerShell의 `Out-File` / `>` 는 BOM을 붙이므로 편집 시 주의.
